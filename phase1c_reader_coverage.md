# Phase 1C data reading layer

`read_run(connection, run_id)` reads a submitted deal, its frozen catalogue and applied commercial profile, and operational evidence available at `deal_runs.as_of_at`. It returns source rows with IDs plus derived numeric facts. It does not approve a deal or create reservations. Call it inside a PostgreSQL `REPEATABLE READ READ ONLY` transaction to prevent a mix of database states. Install `psycopg[binary]>=3.2,<4` to use it.

Source of truth: the current numbered `02-Deal-Desk-Orchestrator-Phase1C.md` on Drive and its `Phase1C-row-fixture-coverage-map.md`. The 11 KB attachment supplied to the coding chat is stale. The reader is a first data layer, not the full agent rule engine.

## Decisions to review before calibration is frozen

- **Freshness:** 24 hours is a provisional maximum age for inventory, digital pool and capacity snapshots, and credit commitments. Configure per source and business profile before generating a large dataset. A stale number is retained as evidence but cannot confirm capacity.
- **Digital quantity and proof:** `quantity` is billed units over the contract, while `configuration_json.units_per_period` is concurrent entitlement demand. The reader requires `quantity = contract_months × units_per_period` and exact product, edition, country, term and unit. `load_provider_evidence(path)` reads a controlled manifest outside salesperson deal input, keyed by `evidence_ref`; exact provider fields, full-term dates and verification within seven days are required before a binding candidate becomes `confirmed_by_date`. A reference string alone does not. The fixture manifest is an invented provider commitment for testing, not a real provider attestation. The thesis generator can create analogous synthetic records, independently of deal inputs, and retain their provenance. A live provider connection is needed only if the system is used for real commercial promises.
- **Shipping:** A receipt expected on a given date is conservatively available for dispatch the *next* allowed workday. Workdays currently follow the lane's weekday list; holidays and supplier calendars are not yet evaluated.
- **Assembly:** The reader checks all resources at one operation sequence on the same day, advances later steps to a later workday, and aggregates shared components within the deal. For this date-level synthetic model, a confirmed component receipt is usable for production on its `expected_date`; the finding names that convention. Capacity is tentative and consumed only in memory. There is no intra-day receipt or workshop schedule, so this is a planning convention rather than a clock-time promise. For each BOM substitute group, one alternative is selected using sufficient fresh stock/confirmed inbound first, then priority and component ID; an uncovered group remains visible as a shortage and alternatives are not double-counted. Cross-location allocation remains outside this version; do not treat a feasible day as a reservation.
- **Compatibility:** Required/excluded products, attribute constraints and required deal fields are evaluated with the typed operator vocabulary in `phase1c_data_contract.yaml`; findings retain status, severity and rule ID. Blocker failures feed the configuration gate, while warnings, unknowns and unsupported predicates remain evidence gaps. Installation eligibility still uses the current country/region fixture convention. Generated catalogue coverage remains open.
- **Commercial rules:** `phase1c_rule_rows.sql` contains narrow test-only rows for the original 14 reader checks. `calibration_config.yaml` contains the accepted synthetic profile numbers; `compile_phase1c_policy.py` validates their boundaries and produces 105 pricing, policy and approval rows across three profiles, including invalid terms, clauses and inactive accounts. `phase1c_policy_decision.py` interprets this complete compiled row set when the reader selects it (or `commercial_rule_mode="compiled"`). It calculates line and deal discounts/margins, credit and overdue AR, terms, clauses, value and late-delivery triggers, then returns hard blocks, evidence gaps and ordered required roles with rule IDs. A hard block or missing evidence withholds the final route. A partial/malformed compiled set raises an error. A required role is a review route, never an actual approval. The 14-case reader contract stays separate; independently authored commercial examples check additional thresholds and conflicting triggers.
- **Deal decision gate (5 October 2026):** `phase1c_deal_decision.py` assembles seven attributed decision sections from a run-scoped reader bundle and the complete compiled commercial profile, including compatibility findings; these sections are not seven agents. It emits a route only when configuration, fulfillment and commercial evidence permit one. Missing proof, stale snapshots, unresolved supplier offers, uncommitted production, late dates, incompatible installation and hard policy blocks remain distinguishable. It makes no reservation or actual approval. The 14 stored reference runs are checked against compiled rules. The first run caught a stale test expectation of six sections; commit `35fd271` corrected it, and [Actions run 37290252824](https://github.com/alialnaggar/dealdeskdata/actions/runs/37290252824) passed the full gate and preceding reader checks. This is a deterministic decision package, not yet the six-agent/Orchestrator runtime, full compatibility/dependency validator or independent evaluation dataset.
- **Cost:** The rollup uses explicit caller-supplied labor rate and overhead fraction and checks the 5% tolerance. Decide the versioned source of those parameters; the example uses 30 EUR/hour and 10% overhead from the calibration scenario.
- **Snapshot completeness:** Invoice snapshots are selected per invoice at or before the run date. A missing invoice or source-wide completeness marker cannot be detected with the current schema. Review that limit for credit conclusions.

The old narrative also describes 30–50 independent adversarial evaluation deals. These 14 database reference cases are implementation checks and do not replace that evaluation set.

**Field calibration gate (4 October 2026):** `phase1c_column_rules.yaml` lists source/basis, generation and validation for all 266 columns in the current 24-table schema. `validate_phase1c_column_rules.py` compares exact table, field, SQL type and nullability coverage in CI. It reports 22 definitions still requiring executable choices before generation; it does not run the written field rules against generated rows. The synthetic 1–8 historical lines/deal weights and pilot mean/bin tolerances are now in `calibration_config.yaml`. Olist's observed consumer late-delivery rate is not an actual-delivery target for this schema, which has no delivered date. Historical credit replay needs frozen as-of evidence.
